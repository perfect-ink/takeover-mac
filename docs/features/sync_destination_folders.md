# Sync destinations: app folder, then location folder

Every sync location's destination is `[settings folder]/[app name]/[location name]`, and the location's name in Sync Settings is that folder's name, so the two always match. For example Serum's `~/Library/Application Support/Xfer` syncs to `Takeover/Serum (Xfer Records)/Application Support`.

- **Names come from the API.** Every path in takeover-site's `public/catalog/apps.yaml` has a `name`. Names start with "User" only for paths in `~/Library` and "Root" only for paths in `/Library`; every other location is named for what it is (`~/.ssh` is "SSH", `~/.zshrc` is "Zsh Config"). A catalog test in takeover-site enforces this. Renaming a location in the catalog reaches existing Macs through Rename and Move, since locations are matched by app and source path. `/api/v1/repository` passes it through; the Mac decodes it as `FileConfig.name` (`Shared/Data/Repository.swift`). The bundled `Takeover/apps-catalog.yaml` is refreshed by `make catalog`.
- **Building To.** `RecipeInstaller` in `Takeover/Views/RecipesView.swift`: `appFolder` is the app's name as shown (`baseName`, so `Ableton (2)` and `Audio Plug-Ins (Users)` share their app's folder), `locationName(for:named:)` is the catalog name or the path's last component, and `destination(appName:from:named:others:)` joins them. If another location already uses that folder, `uniqueDestination` adds the differing part of the path (`Plug-Ins (User)`), then a number. Used when seeding catalog locations, by Add (a sync setting of your own), by Add Location (`Location 2`), and when a new From is picked.
- **Shown name.** `RecipeInstaller.displayName(of:)`: the last component of a To in the settings folder. For a To the user chose elsewhere (an absolute or `~` path) it's the rename label, else the source's name.
- **Changing To.** Every code path that changes a location's To (rename, picking a new From or To, Reset Locations, catalog renames, moving into app folders, a pull from the account) goes through `LinkItemInstaller.changeDestination(of:to:)`. It moves the synced files from the old destination (refusing to replace an existing folder, except with `adoptExisting`; see Catalog renames), moving in two steps when the new place is inside the old one, repoints the source's link when it pointed at the old destination (compared case- and Unicode-insensitively, like the Mac's file system) or when the move just broke it, and only then sets To. If relinking fails the files go back. A link already dangling at a missing old destination is pointed at the new one. Locations change To without asking only when there's no link at the source and nothing at the destination (`LinkItemListView.nothingOnDisk`).
- **Rename** (location's ••• menu, `LinkItemDetailView.commitRename`) renames the destination folder too, through `LinkItemInstaller.changeDestination(of:to:)`. A To outside the settings folder only gets a label.
- **Older locations.** On load, locations still in the old flat layout (`NativeInstruments-Documents`) move to `App/Location` when they aren't linked and nothing is at their old destination (`LinkItemListView.moveIntoAppFolders`).
- **Catalog renames.** When the catalog changes a location's name (same source path), so its destination changes, Sync Settings follows it (`LinkItemListView.followCatalogNames`, run whenever the catalog's apps, paths or names change). A location with nothing on disk just takes the new destination. One that's linked or has files at its destination is listed in a "The catalog renamed …" dialog showing old → new: **Rename and Move** moves each folder in the Takeover folder and relinks it (`moveDestination`). If the new destination already exists (another Mac sharing the settings folder made the move first), it's used as-is: this Mac's old destination is set aside as `<old>-old-<timestamp>` (never deleted) and the link points at the existing one; when the new place is inside the old folder and already there, it just relinks. For a /Library location, an existing synced copy at the new name seeds the local store. Reset Locations and pulls from the account do the same (`adoptExisting: true`); renaming a location yourself still refuses to use a folder that's already there; **Keep Current Names** leaves them. Each answer is remembered per Mac (`CatalogSeen`, in UserDefaults), so a change is asked about once and a location you renamed yourself isn't asked about again after that.
- **Reset Locations.** The ↺ button next to an app's name gives each of its locations the destination it would get today (catalog name, else rename label, else source name), moving the synced files there and relinking linked ones with `moveDestination`, so nothing is lost. It also brings back the app's catalog locations that were removed (`RemovedLocations.forget`). While any location is still in the old layout, a folder button in the sidebar controls does the same for every location (without bringing removed ones back). Failures are listed in one alert; the rest still move.
- **Installing.** An app's page has **Install All** with the ↓ icon while any location isn't linked (links those), and **Uninstall All** with the ↩ icon while any is (unlinks those after one question); both show when some are installed and some aren't. Each location also has its own icon button next to its status: ↓ installs just that location, ↩ uninstalls it (asking what to do with its files first) (`LinkItemDetailView.statusAndButtons`).
- **Both copies exist.** Installing a location whose source is a real folder or file on this Mac while its destination already has a synced copy asks first (`LinkItemInstaller.hasConflict`; one dialog per location, queued for Install All): **Use This Mac's** sets the synced copy aside as `<destination>-old-<date>`; **Use Synced Copy** sets this Mac's copy aside as `<source>-old-<date>` and links to the synced one; **Merge with rsync** runs `rsync -a --update` from this Mac into the synced copy (newer file wins, nothing deleted, `FileOps.merge`), then sets this Mac's original aside and links. Restore still installs without asking (keeps this Mac's copy, as before).
- Tests: `destinationIsAppFolderThenLocationFolder`, `clashingLocationsGetTheDifferingPart`, `locationNameMatchesItsDestinationFolder`, `catalogLocationNamesDecode`, `mergeKeepsBothSidesFilesAndDeletesNothing`, `changingToMovesFilesAndRelinks`, `changingToRepairsALinkToAMissingDestination`, `catalogMoveAdoptsAnExistingDestination`, `catalogMoveIntoASubfolderOfTheOldDestination`, `distinguishingPartIsWhereThePathsDiffer` in `TakeoverTests/TakeoverTests.swift`; takeover-site's `catalog_test.rb` checks every path has a name, unique within its app.
- Limits: other Macs linked to a renamed location's old folder see it as linked elsewhere until they reinstall it.
